# 문자 발송 서비스 비교 — 타스온 · 알리고

교육 안내 문자 자동 발송 서비스 선정을 위한 비교.
양쪽 공개 API 규격·요금표 직접 확인 (2026-08-21 기준).

## 현재 운영 — 무엇을 없애려는가

07:30 발송 자체는 이미 예약으로 나가고 있다. **타스온 콘솔의 예약 기능**을 쓴다.

```
현행 — 담당자가 콘솔에서 예약을 건다

  회차마다   EMS 에서 명단 내려받기 → 타스온 콘솔에 붙여넣기 (100건 한도로 분할)
             → 발송 시각 지정 → 예약 등록
  1~3일차 07:30   예약대로 발송
             └── 발송은 자동. 예약 등록이 매 회차 수동 ──┘
```

자동화 대상은 **발송이 아니라 예약 등록**이다. 명단 추출·붙여넣기·시각 입력이
회차마다 반복되고, 명단 누락과 시각 오입력이 여기서 발생한다.

## 권고

**알리고 전환.** 근거는 요금이 아니라 **예약 등록을 API 로 할 수 있는가**.

- 타스온 예약 — **콘솔에서만 가능. API 규격에 예약 파라미터 없음**
- → 예약 등록 자동화 불가. 자동화하려면 콘솔 예약을 버리고
  **07:30 발송 자체를 우리가 호출**해야 하며, 스케줄러 · 인증 · 배치 분할 ·
  부분 실패 처리가 전부 **우리 몫의 부품**으로 편입
- 알리고 — 예약 등록이 **API 로 제공**. 콘솔 예약의 이점을 유지한 채 등록만 자동화
- 취소 · 리허설 · 잔여 건수 확인도 동일 (타스온 API 불가 / 알리고 제공)

요금 절반은 부차적 근거.

## 갈림길은 예약 API 하나

같은 "집중교육 3일간 매일 아침 07:30 수신" 요건에서 세 갈래로 갈린다.

```
① 현행 (타스온 콘솔) — 사람이 예약을 건다

  회차마다   명단 추출 → 콘솔 붙여넣기 → 예약 등록      ← 없애려는 작업
  1~3일차 07:30   예약대로 발송


② 타스온 자동화 — 우리가 발송을 시작

  전주      사람 검수 → 발송 예정 등록
  1일차 07:30   Vercel Cron → 우리 엔드포인트 → 이력 확인 → 배치1(100) + 배치2(53) → 타스온 API
  2일차 07:30   Vercel Cron → 우리 엔드포인트 → 이력 확인 → 배치1(100) + 배치2(53) → 타스온 API
  3일차 07:30   Vercel Cron → 우리 엔드포인트 → 이력 확인 → 배치1(100) + 배치2(53) → 타스온 API
                └──────────── 3일간 매일, 이 사슬 전부 정상 동작 필요 ────────────┘


③ 알리고 — 시스템이 예약을 걸고, 통신사가 발송한다

  전주      사람 검수 → 시스템이 예약 등록 (rdate/rtime, 153명 1회) → mid 보관
  1일차 07:30   통신사 발송
  2일차 07:30   통신사 발송
  3일차 07:30   통신사 발송
                └── 우리 시스템 관여 없음 ──┘
```

②는 사람 손이 빠지는 대신 **발송 시각마다 우리 시스템이 살아 있어야 한다.**
③은 사람 손도 빠지고 발송 시각 의존도 없다.

| | ① 현행 | ② 타스온 자동화 | ③ 알리고 |
|---|---|---|---|
| 예약 등록 주체 | **사람 (콘솔)** | — (예약 미사용) | **시스템 (API)** |
| 07:30 발송 개시 주체 | 통신사 | **우리 시스템** | 통신사 |
| 우리 시스템 의존 구간 | 없음 | **3일간 매일 07:30** | 예약 등록 시점 1회 |
| 해당 시각 시스템 정지 시 | 정상 발송 | 그날 미발송 | 정상 발송 |
| 회차마다 사람의 수동 작업 | **있음** | 없음 | 없음 |
| 새로 만들어야 하는 부품 | 없음 | **스케줄러·인증·배치·부분실패** | 없음 |

## 우리가 떠맡는 것 — Vercel Cron

타스온 채택 시 07:30 트리거는 **Vercel Cron** 담당.
아래는 Vercel 공식 문서 명시 제약. 예약 API 미사용 시 **전부 우리 발송의 위험으로 편입**.

| Vercel 문서 원문 | 타스온일 때 | 알리고일 때 |
|---|---|---|
| *"Vercel will not retry an invocation if a cron job fails."* | 1회 실패 시 그날 미발송 | 해당 없음 |
| *"Cron job delivery is best effort. … your function does not execute, and no runtime log is created."* | 미발송 사실조차 **로그 미기록** | 해당 없음 |
| *"Cron delivery can also occasionally invoke the same scheduled run more than once."* | 같은 안내 **두 통 발송 가능** | 해당 없음 |
| *"it generates a 404 error. However, Vercel still executes your cron job"* | 경로 오타를 로그로만 인지 | 해당 없음 |
| *"Cron jobs do not follow redirects."* | 인증 미들웨어 리다이렉트 시 발송 불가 | 해당 없음 |
| *"active cron jobs will not be updated"* | **롤백해도 옛 스케줄 계속 실행** | 해당 없음 |

세 번째 항목이 최대 위험. 07:30 동일 안내 2통 수신 시 교육생은 오류로 인식.
문자는 회수 불가.

> QStash 등으로 스케줄러 교체 시 재시도 확보. 단 **재시도는 의도적 재호출**이므로
> 중복 위험 잔존. 스케줄러 교체로 해결되지 않는 문제
> ([docs/02](02-발송-계획.md#cron-을-믿을-수-없는-지점들)).

## API 로 할 수 있는 일의 범위

양쪽 규격 전수 대조. **이 표가 본 문서 근거의 전부.**

| | 타스온 | 알리고 |
|---|---|---|
| 인증 | `tas_id` + `auth_key` | `user_id` + `key` |
| 발송 | `POST /tas-api/send`<br>`send_type` = SM / LM / **EM** | `POST /send/`<br>동일 내용 **1,000명** |
| 수신자별 다른 내용 | — | `POST /send_mass/` 500명 |
| 본문 치환 | — | `destination` |
| **예약 발송** | **없음** | `rdate` (YYYYMMDD) · `rtime` (HHMM) |
| **예약 취소** | **없음** | `POST /cancel/` — `mid` 기준 |
| **테스트 모드** | **없음** | `testmode_yn=Y` |
| **잔여 건수 조회** | **없음** — 발송 요청 시에만 확인 | `POST /remain/` → `SMS_CNT` · `LMS_CNT` · `MMS_CNT` |
| 발송 이력 조회 | `POST /tas-api/result`<br>`workday` (**날짜 단위**) + `page` | `POST /list/`<br>`start_date` + `limit_day` |
| 수신자별 결과 조회 | 동일 API `result_type=list` | `POST /sms_list/` — **`mid` 기준** |
| 카카오 알림톡 | `POST /tas-api/kakaosend` — `template_code` | 본 규격 페이지에 없음 |
| 1회 요청 최대 수신자 | **문서 미명시** (콘솔 기준 100건) | **1,000명** (문서 명시) |

굵은 항목이 결론의 근거. **타스온 API 가능 범위는 발송·조회 둘뿐.**

## 실물 발송 없는 리허설 가능

알리고 `/send/` · `/send_mass/` 에 **`testmode_yn=Y`** 존재.
규격 표현 그대로 *"과금프로세스와 실제문자 전송을 제외"*, 나머지 경로는 동일 실행.

핵심 — **문자는 회수 불가. 그래서 현재 설계는 실물 발송을 검증 수단으로 사용 중.**

```
현재 계획 (docs/02 도입 순서)
  1단계  발송 이력 구축
  2단계  첫 몇 회차 병행 운영 — 실물은 콘솔 예약, Cron 은 로그로만 확인
  3단계  Cron 정시 동작 확인 후 전환
                    ↑
      이 확인은 회차가 실제로 돌아야만 가능
```

`testmode_yn=Y` 적용 시 — **실제 명단 · 실제 코드 경로 · 실제 예약 시각**으로 전 구간 검증.
문자 미발송, 요금 미부과.

| | 타스온 | 알리고 |
|---|---|---|
| 실물 없는 발송 코드 검증 | **불가** — 발송해야 확인 | `testmode_yn=Y` |
| 코드 결함 발견 시점 | 교육생 수신 후 | 개발 중 |
| 회차 전체 리허설 | 실제 회차 도래 필요 | 상시 가능 |
| 병행 운영 기간 | 3~4회차 | 리허설로 대체 가능 |

교육생 137명에게 잘못된 문자 발송 대 테스트 모드 137건 무음 통과의 차이.
**회수 불가능한 수단을 테스트에 사용하지 않아도 됨.**

## 발송 전 사전 점검 · 발송 후 대조

### 잔여 건수 — `/remain/`

알리고 — **`SMS_CNT` · `LMS_CNT` · `MMS_CNT`** 로 종류별 발송 가능 건수 반환.
타스온 — 해당 엔드포인트 없음. 잔액은 **발송 요청 후에만** 확인 가능.

```
알리고     예약 등록 전 /remain/ 호출 → LMS_CNT 153 미만이면 담당자 알림
타스온     07:30 호출 → 잔액 부족 실패 → 그날 미발송
```

07:30 은 무인 시간대. **잔액 부족은 코드로 방어 불가한 실패.
사전 조회 시 근무 시간에 사전 발견 가능.**

### 결과 조회 축 — `mid` 대 `workday`

양쪽 모두 수신자별 결과 제공. 차이는 **조회 기준**.

| | 타스온 | 알리고 |
|---|---|---|
| 조회 기준 | `workday` — **그날 발송 전체**를 `page` 로 순회 | `mid` — **해당 묶음만** 직접 조회 |
| 우리 이력과의 대응 | 날짜로 조회 후 우리 건 선별 필요 | `발송묶음` 1건 ↔ `mid` 1개 |

[docs/04](04-발송이력.md) 의 발송묶음과 `mid` 가 1:1 대응. 조회 1회로 종결.

### `발송중` 상태 해소 가능

[docs/04](04-발송이력.md#중복-방지-규칙) 미결 항목 (원문 인용).

> `발송중` 인 채로 오래 남은 건은 사람이 확인한다. 자동으로 풀지 않는다 (2026-08-18 결정).
> 자동 복구를 넣으려면 "응답을 못 받았지만 실제로는 나갔다"를 판별할 방법이 있어야 한다.

알리고 — 예약 등록 응답으로 `mid` 반환. 응답 미수신 시에도 `/list/` 로 등록 여부 확인,
`/sms_list/` 로 수신자별 상태 확정 가능.
**사람의 수동 판단 항목이 조회 1회로 대체.**

## 만들지 않아도 되는 부품

알리고 전환 시 **설계에서 소멸**. 구현 · 테스트 · 운영 · 장애 대응 전 영역.

| 부품 | 타스온에서 필요한 이유 | 알리고 |
|---|---|---|
| Vercel Cron 스케줄 | 예약 API 부재로 07:30 직접 호출 필요 | **불필요** |
| UTC 시각 변환 (`30 22 * * *`) | Cron 은 UTC 고정. 07:30 KST 가 전날 22:30 으로 표기 | **불필요** |
| `CRON_SECRET` 인증 | 공개 URL 개방에 따른 보호 필수 (아래) | **불필요** |
| 배치 분할 (100 + 53) | 1회 요청 한도 콘솔 기준 100건 | **불필요** (1,000명) |
| 부분 실패 상태 · 배치별 재시도 | 분할 시 일부만 발송된 상태 발생 | **불필요** |
| 스케줄러 교체 대비 (QStash 등) | Cron 실패 관찰 시 교체 계획 상시 보유 필요 | **불필요** |
| 잔액 부족 사후 처리 | 사전 조회 수단 없음 | **불필요** (`/remain/`) |
| 발송 이력 | 중복 · 부분 실패 방어의 유일 장치 | **필요** — 단 성격 상이 |

발송 이력은 양쪽 모두 구축 대상. 차이는 역할.

- 타스온 — **중복 발송 방어선**
- 알리고 — **`mid` 와 결과의 기록**

방어선은 오류 시 사고 발생, 기록은 해당 없음.

## 공개 엔드포인트 소멸

Cron 은 **공개 URL 에 GET 요청** 전송. 타스온 방식은 인터넷에서 호출 가능한
발송 엔드포인트 상시 개방 구조.

```
GET https://<ems>/api/cron/send-sms      ← 주소 인지자는
                                            교육생 전원에게 문자 발송 가능
```

회수 불가 · 비용 발생. `CRON_SECRET` 으로 방어 가능하나 **방어 대상이 1개 증가한 것은 동일.**
알리고 예약 사용 시 해당 엔드포인트 자체가 불필요 → **공격면 소멸.**

## 배치 분할과 부분 실패

수신자 **153명** (교육생 137명 + 고정 수신자 16명).

| | 1회 요청 한도 | 153명 발송 | 부분 실패 |
|---|---|---|---|
| 타스온 | **문서 미명시** · 콘솔 기준 100건 | **2회 분할** | **발생** |
| 알리고 | **1,000명** (문서 명시) | 1회 | 미발생 |

타스온 측 문제는 100 이라는 수치가 아니라 **규격에 수치 자체가 없다는 점**.
배치 크기가 문의 답변에 종속. 답변 변경 시 코드 변경
([docs/03](03-확인-필요.md) 문의 2번).

분할 시점에 **일부 발송 · 일부 실패 상태** 발생.

```
07:30  배치1 (100명) 성공
       배치2 ( 53명) 실패
              ↓
   전체 재실행 시 배치1 의 100명 중복 수신
              ↓
   → 배치 단위 이력 + "실패분만 재발송" 로직 필요
```

알리고 — 153명 단일 요청 처리로 **해당 상태 정의상 미발생.**
[docs/04](04-발송이력.md) 부분 실패 절 전체 불필요.

| 예약 등록 최소 시점 | — | 발송 **10분 전**까지 등록 가능 |

우리 운영은 전날 또는 전주 등록 → 10분 제약 무관.

타스온 콘솔 예약 병행 시 **취소가 두 곳에서 발생.** 콘솔 삭제 + 시스템 상태 변경.
사람이 한 단계 누락 시 **이력과 실제 불일치**
([docs/04](04-발송이력.md#예약을-걸어둔-뒤-상황이-바뀌면)).
알리고 — `mid` 하나로 취소와 이력 갱신 동시 처리.

## 실패 시나리오 대조

| 상황 | 타스온 (Cron 직접 호출) | 알리고 (예약) |
|---|---|---|
| 07:30 서버 장애 | **그날 미발송** | 정상 발송 |
| 07:30 직전 배포 진행 | **그날 미발송 가능** | 정상 발송 |
| 잘못된 배포 롤백 | 옛 Cron 스케줄 계속 실행 | 영향 없음 |
| Cron 미실행 | 미발송 + **로그 미기록** | 해당 없음 |
| Cron 중복 호출 | 이력 방어 실패 시 **2통 발송** | 해당 없음 |
| 발송 시각 잔액 부족 | **그날 미발송** — 사전 인지 수단 없음 | 등록 전 `/remain/` 사전 감지 |
| 153명 중 배치2 실패 | 부분 실패 → 실패분 선별 재발송 | 부분 실패 미발생 |
| 응답 미수신으로 `발송중` 잔류 | 사람이 판단 (자동 복구 보류) | `mid` 로 상태 확정 |
| 발송 코드 수정 후 검증 | 실물 발송 필요 | `testmode_yn=Y` |
| 교육 전일 취소 결정 | 예약 미등록 시 단순 / 등록 시 사람이 콘솔 처리 | `/cancel/` |
| 발송 30분 전 ZOOM 비번 변경 | 예약 미등록 시 본문 수정 | 취소 후 재등록 |
| 발송 3분 전 ZOOM 비번 변경 | **본문 수정 가능** | 취소 불가 — 정정 문자 발송 |

마지막 항목이 **타스온 우위 칸**. 예약 미등록 방식의 부수 효과로 발송 직전까지 수정 가능.
단 그 대가가 위 표의 나머지 전부.

## 타스온이 앞서는 것

일방적 정리는 검토가 아님. 규격에서 확인된 타스온 우위 3건.

### ① 이메일 발송 타입 `EM`

- 타스온 `send` 의 `send_type` 에 **`EM`(이메일)** 포함 → 문자·메일 **동일 API** 처리
- 메일 발송 경로는 미해결 항목. 기관 메일이 정부 통합메일, SPF 가 `-all` 이라
  외부 발송 시 수신 측 거부 ([docs/02](02-발송-계획.md#메일-발송-경로))
- 단 **타스온 `EM` 도 즉시 해결책은 아님.** 발신 도메인이 `nia.or.kr` 이면
  타스온 역시 SPF 허용 목록 밖 → 동일 거부. 발신 도메인 변경 또는 SPF 추가 필요
- **확인 가치 있음. 확인 전 폐기 불가한 선택지.**

### ② 카카오 알림톡 API `kakaosend`

- 타스온 — `POST /tas-api/kakaosend` 를 `template_code` 와 함께 문서화
- 알림톡 — LMS 대비 저단가, 도달 형태 우수
- 알리고 — 카카오톡 상품 메뉴 존재. 단 **본 SMS API 규격 페이지에는 없음**
- 알리고 알림톡 API 존재 여부·규격 **별도 확인 필요**

### ③ 발송 직전까지 본문 수정

예약 미등록 방식의 부수 효과. 위 시나리오 표 마지막 항목.

**3건 모두 현행 발송에 미사용.** ①②는 확인 완료 후 실효 발생, ③은 알리고 `/cancel/` 로 대체.
그럼에도 결론에서 미제외.

## 타스온 유지 시

전환 없이도 자동 발송 구현 가능. 단 아래 수용 필요.

```
· 07:30 발송이 Vercel Cron 의 best effort 에 종속 (재시도 없음, 무로그 실패 가능)
· 중복 호출 대비 이력이 사고 방어의 유일 장치
· 153명 2배치 분할 + 부분 실패 별도 처리 — 배치 크기는 문의 답변에 종속
· 공개 발송 엔드포인트 상시 개방·유지
· 발송 코드 검증을 실물 발송으로 수행 — 테스트 모드 없음
· 잔액 부족 사전 인지 불가
· 시스템 정지 대비 시 콘솔 예약 병행 필요 → 회차당 3회 수동 작업 + 이력 불일치 위험
```

| | 수동 작업량 | 시스템 정지 시 |
|---|---|---|
| 타스온 API 단독 | 0 | 그날 미발송 |
| 타스온 API + 콘솔 예약 병행 | **회차당 3회** | 정상 발송 (단 이력 수동 갱신) |
| 알리고 예약 | 0 | 정상 발송 |

## 확인 필요 항목

기술 검토로 답할 수 없는 항목.

- 타스온 사용의 계약 · 기관 지정 구속 여부
- 발신번호 재등록 절차 진행 가능 여부
- **알리고 알림톡 API 존재 여부·규격** — 타스온에는 `kakaosend` 존재.
  장기 알림톡 전환 고려 시 결론 변경 가능 항목
- **타스온 `EM` 의 기관 메일 발송 가능 여부** — SPF 허용 목록 문제 잔존.
  전환 여부와 무관하게 메일 경로는 별도 결정
- 알리고 예약 **최대 사전 등록 기간** — 3일치 전주 일괄 등록 가능 시 등록 시점도 1회로 축소
- `/list/` 의 `limit_day` 최대값 — 이력 대조 가능 기간

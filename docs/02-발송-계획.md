# 발송 계획

안내서 PDF 생성 다음에 붙일 것. 아직 구현하지 않았다.

## 무엇을 자동화하는가

지금은 회차마다 이렇게 한다.

```
EMS 에서 교육생 명단을 구글시트로 내려받는다
      ↓
번호를 100개씩 끊어 타스온 콘솔에 붙여넣는다
      ↓
교육 전주에 안내 메일을 보낸다
      ↓
교육 당일 아침에 문자를 예약한다
```

명단이 EMS 에 이미 있으므로 내려받을 이유가 없다. EMS 안에서 회차를 고르고 값 네 개를
넣으면 메일과 문자가 나가게 한다.

## 이메일과 문자는 성격이 다르다

| | 이메일 | 문자 |
|---|---|---|
| 언제 나가나 | 교육 전주 | 교육 당일 07:30 |
| 경로 | 기관 메일 (아래 [메일 발송 경로](#메일-발송-경로)) | 타스온 API |
| 1회 건수 제한 | 확인 중 | **콘솔 기준 100건** (API 는 문의 중) |
| 잘못 보냈을 때 | 되돌릴 수 없다 | 되돌릴 수 없다 |

## 타스온 API — 확인된 규격

공개 문서(v1.3, <https://www.tason.com/developer/api>)를 읽고 확인한 것이다.
**규격 문서를 따로 요청할 필요가 없다.**

```
POST https://api.tason.com/tas-api/send

Body(JSON)
  tas_id      계정 식별자
  auth_key    인증 키          ← 이 둘이 인증을 겸한다
  send_type   SM(단문) / LM(장문)
  data[]      user_name · user_email(수신 휴대폰번호) · map_content
              sender(발신번호) · sender_name(선택)
```

**여기서 나오는 결론 두 가지.**

**① 예약 발송 파라미터가 없다.** 알리고의 `rdate`/`rtime` 같은 필드가 규격에 없다.
즉 07:30 발송은 **우리가 그 시각에 API 를 호출해야 한다.**

**② 예약 조회·취소 API 도 없다.** 발송 결과 조회만 있다. 잘못 건 예약을 프로그램으로
되돌릴 수 없다는 뜻이다.

에러 코드 `41` 은 미인증 발신번호이거나 수신자가 비었을 때 나온다
(*"wrong sender data - {발신값} or blank receiver data"*).

## 07:30 발송을 무엇이 시작시키나

예약 API 가 없으므로 **Vercel Cron** 으로 우리 엔드포인트를 부른다.
EMS 가 올라간 Vercel 팀은 **Pro** 요금제다(2026-08-07 확인). 그래서:

- 실행 시각이 **분 단위로 정확**하다 (Hobby 는 ±59분이라 07:30 이 08:29 까지 밀린다)
- 상업적 이용에 제한이 없다 (Hobby 는 *"personal, non-commercial use"* 다)

**시간대는 항상 UTC 다.** 07:30 KST 로 걸려면 이렇게 쓴다.

```json
{ "crons": [ { "path": "/api/cron/send-sms", "schedule": "30 22 * * *" } ] }
```

`30 22` 가 왜 07:30 인지 헷갈리기 쉬운 자리다. UTC+9 를 빼면 전날 22:30 이다.

### Cron 을 믿을 수 없는 지점들

Vercel 문서가 밝히는 것들이다. 설계에 반영해야 한다.

| 사실 | 원문 | 대응 |
|---|---|---|
| 실패해도 재시도하지 않는다 | *"Vercel will not retry an invocation if a cron job fails."* | 실패 감지 필요 |
| 아예 안 돌 수 있다 | *"Cron job delivery is best effort. … your function does not execute, and no runtime log is created."* | **로그조차 안 남는다** |
| 두 번 부를 수 있다 | *"Cron delivery can also occasionally invoke the same scheduled run more than once."* | 발송 이력 필수 |
| 경로가 없어도 실행된다 | *"it generates a 404 error. However, Vercel still executes your cron job"* | 경로 오타를 로그로만 안다 |
| 리다이렉트를 안 따라간다 | *"Cron jobs do not follow redirects."* | 인증 미들웨어 주의 |
| 롤백해도 안 바뀐다 | *"active cron jobs will not be updated"* | 되돌려도 옛 스케줄이 돈다 |

### 엔드포인트를 보호해야 한다

Cron 은 **공개 URL 에 GET 요청**을 보낸다. 보호하지 않으면 그 주소를 아는 누구나
호출해 **교육생 전원에게 문자를 발송시킬 수 있다.** 되돌릴 수 없고 비용도 나간다.

`CRON_SECRET` 환경변수를 넣으면 Vercel 이 `Authorization: Bearer <값>` 헤더를 붙여
호출한다. 엔드포인트에서 대조한다.

```ts
export function GET(request: NextRequest) {
  const auth = request.headers.get('authorization');
  if (auth !== `Bearer ${process.env.CRON_SECRET}`) {
    return new Response('Unauthorized', { status: 401 });
  }
  // 발송
}
```

### 검토했다가 접은 것

| 방법 | 왜 안 썼나 |
|---|---|
| AWS EventBridge + Lambda | 하루 한 번 HTTP 호출에 AWS 계정·IAM·Lambda 배포가 통째로 늘어난다 |
| Upstash QStash | 재시도 3회와 DLQ 가 매력적이지만 계정이 하나 는다. **Cron 이 실제로 실패하는 게 관찰되면 그때 교체한다** — 스케줄러만 갈아끼우면 되므로 비용이 작다 |

> QStash 로 갈아탈 때 참고: `CRON_TZ=Asia/Seoul 30 7 * * *` 처럼 시간대를 그대로 쓸 수 있고,
> 재시도 간격이 `min(86400, e^(2.5n))` 이라 기본 3회면 마지막이 약 33분 뒤다. 교육 시작
> 09:30 전에 끝나므로 기본값이 적당하다. 4회차는 6시간 뒤라 의미가 없다.

## 발송 이력 — 중복 발송을 막는 유일한 수단

**스케줄러가 해결해주지 않는다.** Cron 은 중복 호출할 수 있고, QStash 로 바꾸면 재시도
때문에 **일부러** 다시 부른다. 어느 쪽이든 우리 쪽에서 막아야 한다.

```
문자를 보내기 전에 이력을 본다
    이미 완료   → 건너뛴다
    아직 미발송 → 보내고 완료로 기록
```

이게 있으면 몇 번을 불려도 문자는 한 번만 나간다. 없으면 어떤 스케줄러를 써도 여러 번 나간다.

### 100건 제한이 부분 실패를 만든다

137명이면 100 + 37 로 쪼개야 한다. 쪼개는 순간 **일부만 나가고 일부는 실패한 상태**가 생긴다.
배치 2 만 실패했는데 처음부터 다시 돌리면 배치 1 의 100명이 문자를 두 번 받는다.

이력이 있으면 이렇게 풀린다.

```
07:30  Cron → 엔드포인트
         ├ 배치1 (100명) 성공 → 이력에 완료 기록
         └ 배치2 (37명)  실패 → 이력에 미발송 기록
                                  ↓
                        실패를 응답으로 알린다
                                  ↓
              (재시도가 있는 스케줄러라면) 이력을 보고 배치2 만 재발송
```

> 수작업으로도 이미 겪는 문제다. 100개씩 끊어 붙여넣다 두 번째 묶음에서 헷갈리면 똑같이
> 벌어진다. 다른 점은 사람은 대개 이상함을 눈치채고 기계는 눈치채지 못한다는 것이다.

### 어디에 기록하나

**EMS 가 이미 쓰는 DB 에 표 하나를 더한다.** 새 저장소를 들일 이유가 없다 — EMS 는 이미
회차·교육생·연락처·체크리스트 토큰을 갖고 있다.

```
발송이력
  회차ID | 교육생ID | 종류 | 상태 | 발송시각 | 응답
  ───────┼─────────┼─────┼──────┼─────────┼──────
                          대기 → 발송중 → 완료
                                        ↘ 실패(사유)
```

DB 종류는 EMS 코드를 받아 확인한다.

## 실행 시간은 여유롭다

Vercel 함수는 Pro 기준 기본 300초, 최대 800초다. 137명을 100+37 두 번 호출하는 정도는
몇 초면 끝난다. 다만 **타스온 응답이 느리면 얘기가 달라져** 문의 항목에 넣어두었다.

요청 본문은 4.5MB 제한이 있다. 현재 규모에서는 무관하다.

## 메일 발송 경로

공개 DNS 조회로 확인한 것이다(2026-08-07).

```
nia.or.kr MX    gcmx01~05.govkorea.kr        ← 정부 통합메일
nia.or.kr SPF   v=spf1 ip4:... include:ozspf.ozmailer.com -all
```

**읽히는 것 셋.**

1. **정부 통합메일이다.** 이런 시스템은 외부 프로그램의 SMTP 접속을 정책적으로 막는 것이 보통이다
2. **SPF 끝이 `-all` 이다.** 허용 목록 밖에서 그 주소로 보내면 **수신 측이 거부한다.**
   우리 서버에서 그냥 보내면 교육생 메일함에 도착조차 못 한다
3. **`ozmailer` 가 이미 허용 목록에 있다.** 대량 발송 서비스를 이미 쓰고 있다는 뜻이고,
   그 경로는 SPF 문제가 없다

그래서 물어볼 것이 "SMTP 를 열어달라"가 아니라 **"이미 쓰는 대량 발송 경로를 우리도 쓸 수
있나"** 로 바뀐다. [docs/03](03-확인-필요.md) 참고.

## 승인은 없애지 않는다

줌 링크 하나 틀리면 교육생 전원이 못 들어온다. 발송 화면에서 미리보기를 확인하고 버튼을
누르는 것이 승인이다. 화면에는 발송문 전문과 함께 **기계가 미심쩍게 본 것**을 같이 싣는다 —
"줌 링크가 지난 회차와 동일합니다" 같은 것.

## 도입 순서

실물 문자는 되돌릴 수 없다. 한 번에 넘어가지 않는다.

```
1단계  발송 이력부터 만든다        ← 스케줄러 선택보다 먼저
2단계  첫 몇 회차는 병행 운영
         실제 문자 → 타스온 콘솔 예약 (검증된 경로)
         Cron     → 같이 돌리되 로그로만 확인
3단계  Cron 이 제때 도는 것이 확인되면 전환
```

병행 단계에서도 이득이 있다 — 시스템이 **발송용 파일을 자동으로 만들어주면** 사람은
업로드만 하면 된다. 번호를 100개씩 끊어 붙여넣는 일이 사라진다.

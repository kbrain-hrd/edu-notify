# 발송 이력

**중복 발송을 막는 유일한 장치다.** 스케줄러가 대신해주지 않는다 —
Cron 은 같은 시각을 두 번 부를 수 있고, 재시도가 있는 스케줄러는 일부러 다시 부른다.

구현 전 검토용 문서다. 상태 전이와 중복 방지 규칙은 나중에 바꾸기 어려우므로 먼저 합의한다.

## 무엇을 발송하는가

한 회차에 **문자 3건과 메일 1건**이 나간다.

```
교육 전주        메일 1건   입과안내 + 별첨 PDF 2개
1일차 07:30      문자       당일 안내
2일차 07:30      문자       당일 안내
3일차 07:30      문자       당일 안내
```

문자에는 **첨부가 없다.** 별첨 PDF 는 메일에만 붙는다.

### 양식은 하나다

문자와 메일은 **같은 내용**을 담는다. 회차마다 바뀌는 것은 변수뿐이다.

```
바뀌는 것   과정명 · 일시 · ZOOM 접속 링크 · ZOOM ID/비번 · 입실 시각
고정        인사말 · 취소 접수 절차 · 지원 연락처
채널 차이   메일에만 별첨 PDF 2개
```

**과정명은 통째로 바뀐다.** 등급·과정·회차·교육 구분·일차가 모두 회차마다 다르다.

```
AI 챔피언 그린(초급) 종합과정 5회차 집중교육 3일차
└─ 등급 ──┘└─ 과정 ─┘└회차┘└─ 교육 ─┘└일차┘
```

본문에 **두 번** 나온다 — 첫 문단의 안내 문장과 `* 과정명:` 항목이다. 한 곳만 고치는
실수가 나오기 쉬운 자리이므로 같은 값을 두 곳에 넣는다.

그래서 **값을 한 번 입력해 문자·메일·안내서 PDF 세 곳에 함께 흘려보낸다.** 지금은 PPT 와
문자를 따로 적어 어긋날 여지가 있는데 그 위험이 사라진다.

## 예약을 누가 하는가 — 구조가 갈린다

문자는 **전날 예약을 걸어 다음날 07:30 에 받게** 한다.

```
1일차분   전주에 예약 등록    →   1일차 07:30 발송
2일차분   1일차에 예약 등록   →   2일차 07:30 발송
3일차분   2일차에 예약 등록   →   3일차 07:30 발송
```

문자 발송 서비스에 예약 API 가 있느냐에 따라 이력의 성격이 달라진다.

| | 예약 API 있음 (알리고 등) | 예약 API 없음 (타스온) |
|---|---|---|
| 우리가 하는 일 | 전날 예약 등록 후 끝 | **매일 07:30 에 직접 호출** |
| 우리 시스템이 죽으면 | 문자는 그대로 나감 | **그날 발송 실패** |
| 이력에 남는 것 | 예약번호 · 예약시각 | 발송 시도 시각 · 응답 |
| 위험 구간 | 예약 등록 순간뿐 | **3일 연속 07:30** |

**예약 API 가 없으면 위험이 3배가 된다.** 하루만 시스템이 죽어도 그날 교육생 전원이
안내를 못 받는다. 이력만으로는 못 막는 문제이므로 [docs/02](02-발송-계획.md) 의
사전 알림·병행 운영이 함께 필요하다.

## 수신자

```
교육생 명단 (EMS)  +  고정 수신자 16명
```

**고정 16명은 회차와 무관하게 항상 들어간다.** 운영진·강사 등이다.

- **발송은 교육생과 똑같이 한다.** 받는 내용도 시각도 같다
- 교육생 명단과 겹칠 수 있으므로 **번호 기준으로 중복을 제거한다**
- 이력에는 `교육생` / `고정` 구분만 남긴다. 집계할 때 나눠 세기 위해서다 —
  "교육생 137명 중 3명 실패" 를 답하려면 고정 16명이 섞이면 안 된다
- 이 번호들은 개인정보다. **저장소에 두지 않는다** — EMS 설정이나 환경변수에 둔다

## 무엇을 적는가

두 층으로 나눈다.

```
발송묶음  (회차 · 일차 · 채널 당 1건)
    회차ID · 일차(1~3, 메일은 없음) · 채널(문자/메일)
    본문 전문 · 첨부 목록(메일만)
    예약시각 · 발신번호 · 등록시각 · 등록한 사람
    상태 · 외부 예약번호(예약 API 를 쓸 때)

발송대상  (수신자 1명당 1건)
    묶음ID · 수신자 · 구분(교육생/고정)
    상태 · 발송시각 · 응답코드 · 실패사유
```

### 왜 본문을 묶음에 두는가

단체 발송이라 **전원에게 같은 글자**가 나간다(개인 이름이 들어가지 않는다). 137명 행마다
같은 본문을 복사할 이유가 없다.

### 왜 완성된 글자를 저장하는가

**보낸 문자를 그대로 한 부 복사해 두는 것이다.** 양식과 그때 넣은 값만 남기면 안 된다.

```
8/12   5회차 3일차 문자 발송
8/25   6회차 준비하며 양식 수정 (문의처 번호가 바뀌어서)
9/01   교육생 문의 — "8/12에 받은 문자 링크로 못 들어갔다"
```

양식만 남겼다면 이 시점에 **8/12 에 실제로 무엇이 찍혔는지 복원할 수 없다.** 양식이 이미
바뀌었으므로 지금 조립하면 그때와 다른 글자가 나온다.

계약서 사본을 남기는 것과 같다. 빈 양식과 기입값만 갖고 있으면, 양식이 바뀐 뒤에는 그때
무엇을 썼는지 증명하지 못한다.

> 개인 이름이 들어가는 문구로 바뀌면 이 결정을 다시 해야 한다. 사람마다 글자가 달라지므로
> 대상 행에도 본문이 필요하다.

## 상태 전이

**묶음**

```
초안 ─(사람이 발송 누름)→ 발송중 ─→ 완료
                            │
                            └─→ 부분실패 ─(재시도)→ 완료
                            └─→ 실패
```

**대상**

```
대기 ─→ 발송중 ─→ 완료
                └─→ 실패(사유)
```

`발송중` 이 따로 있는 이유는 **중복 호출 때문**이다. 요청을 보냈는데 응답을 못 받은 상태와,
아직 안 보낸 상태를 구분하지 못하면 같은 사람에게 두 번 보낸다.

## 중복 방지 규칙

보내기 전에 대상 행을 본다.

| 상태 | 처리 |
|---|---|
| `완료` | **건너뛴다** |
| `발송중` | **건너뛴다** — 응답을 못 받았을 뿐 나갔을 수 있다 |
| `실패` | 다시 보낸다 |
| `대기` | 보낸다 |

`발송중` 을 건너뛰는 것이 핵심이다. 다시 보내는 쪽이 안전해 보이지만, **문자를 두 번 받는
것이 안 받는 것보다 나쁜 상황**이 있다 — 07:30 에 같은 안내가 두 통 오면 교육생은 뭔가
잘못됐다고 생각한다.

`발송중` 인 채로 오래 남은 건은 **사람이 확인한다.** 자동으로 풀지 않는다 (2026-08-18 결정).
자동 복구를 넣으려면 "응답을 못 받았지만 실제로는 나갔다"를 판별할 방법이 있어야 하는데,
발송 결과 조회 API 의 조회 가능 기간을 확인하기 전에는 그 판별을 신뢰할 수 없다.

## 부분 실패

1회 요청 최대 건수를 넘으면 나눠 보낸다(타스온 콘솔 기준 100건, API 한도는 문의 중).
쪼개는 순간 **일부만 나간 상태**가 생긴다.

```
07:30  배치1 (100명) 성공 → 대상 100건 완료
       배치2 ( 37명) 실패 → 대상 37건 실패
                              ↓
                    묶음 상태 = 부분실패
                              ↓
              재시도하면 실패한 37건만 다시 보낸다
```

**처음부터 다시 돌리면 100명이 두 번 받는다.** 이력이 그것을 막는다.

## 답할 수 있어야 하는 것

이력을 이렇게 설계하는 이유다. 아래에 답하지 못하면 구조가 잘못된 것이다.

```
· 8/26 그린 5회차 2일차 문자가 몇 시에, 몇 명에게 나갔나
· 안 간 사람이 있나. 있다면 왜
· 그때 실제로 나간 글자가 무엇인가
· 교육생 137명 중 실패 3건은 누구이며 결번인가 수신거부인가
· 같은 안내가 두 번 나간 적이 있나
```

## 예약을 걸어둔 뒤 상황이 바뀌면

흔히 일어나는 일이라 설계에 넣어야 한다.

```
교육이 취소됨
ZOOM 링크·비번이 바뀜
일정이 밀림
```

이미 예약을 등록한 뒤라면 **취소하고 다시 걸어야** 한다. 그런데 타스온에는 예약 취소 API 가
없다 — 콘솔에서 사람이 취소해야 한다. 그러면 이력과 실제 상태가 어긋난다.

그래서 이력에 **외부 예약번호**를 남긴다. 사람이 콘솔에서 취소했을 때 어느 예약을 지운
것인지 대조할 수 있어야 한다. 예약 취소 API 가 있는 서비스라면 이 과정이 자동이 된다.

## 아직 정하지 않은 것

- **DB 종류** — EMS 코드를 받아 확인한다. 표 구조는 그와 무관하게 위와 같다
- **1회 요청 최대 건수** — 타스온 문의 중. 배치 크기가 여기서 정해진다
- **`발송중` 을 얼마나 지나면 이상으로 볼지** — 응답 지연 시간 답변이 오면 정한다
- **실패 건을 누가 어떻게 보는가** — 슬랙인지 화면인지
- **보관 기간** — 개인정보라 무기한 두지 않는다
- **회차 정보를 어디서 가져오는가** — 과정명·일시를 EMS 가 이미 갖고 있으면 자동으로
  채운다. 없으면 사람이 매번 입력한다
- **문자 3건을 언제 만드는가** — 회차 등록 시 3건을 한 번에 만들어 두는지, 매일 하나씩
  만드는지. 앞쪽이면 값이 바뀌었을 때 세 건을 모두 고쳐야 한다
- **메일 발송 시점** — "교육 전주" 의 정확한 시점과, 사람이 눌러 보내는지 예약인지
- **수신거부·결번 처리** — 실패한 사람에게 다시 보낼지, 다른 경로로 알릴지
